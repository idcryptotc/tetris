# Plan.md — отложенные мысли и планы

Место для «отложенных» мыслей и идей, которые пока не реализованы, и для текущего плана работы. Агенты: перед началом работы по отложенной идее сверяйтесь с этим файлом. Статусы: «в работе» — план согласован, реализуется; «отложено» — идея зафиксирована, пока не берёмся.

## Адаптивный рендер для Windows Terminal — Готово (закоммичено)

**Проблема.** Строка `system("mode con cols=80 lines=25")` в Windows 11 в Windows Terminal не работает (в консоли Win10 — работает). Терминал содержит вкладки, его размер меняется пользователем; запретить ресайз окна и убрать вкладки из кода приложения нельзя (окно принадлежит хосту). Принудительно сменить хост (например, в conhost) из кода тоже нельзя — это настройка ОС («Терминал по умолчанию»).

**Решение.** Текущий режим (фиксированные 80×25 через `mode con`) остаётся без изменений — в Win10/conhost он работает. Параллельно добавляется второй, адаптивный, режим. Выбор — рантайм-детект Windows Terminal (не по версии ОС: WT есть на Win10, conhost — на Win11). Механизм переопределения (флаг ОС / условная компиляция) решим позже — код строится так, чтобы решение стоило 5 строк.

### Детект хоста

- `GetEnvironmentVariableW(L"WT_SESSION")` — переменную задаёт WT всем хостируемым процессам (задокументировано в WT);
- запасной — `TERM_PROGRAM == WindowsTerminal`;
- третий уровень (добавлен после диагностики: при запуске **с повышенными правами** UAC пересобирает окружение и обе переменные не пробрасываются, хотя процесс реально в WT) — класс окна консоли: `GetClassNameW` == `PseudoConsoleWindow` (класс conpty; у классической консоли — `ConsoleWindowClass`). Не зависит от окружения, покрывает все conpty-хосты (WT, терминал VS Code и т.п.). Обход дерева предков (вариант, который пробовали первым) отброшен: 32-битный процесс + MSIX-упаковка WT мешали `OpenProcess`, а класс окна проще и надёжнее.

### Изменения

- [x] 1. **`Console.h`:** `enum class ConsoleMode { Fixed, Adaptive }` (Fixed = текущий); в `ConsoleRenderer` — поля `mode` и `frameOffset` (смещение кадра в буфере), `csbi` теперь инициализируется через `GetConsoleScreenBufferInfo` (было мёртвым: `DoubleBufferingBegin` передавал `{0,0}` в `SetConsoleScreenBufferSize`).
- [x] 2. **`ProgramSettings()`:** детект conpty-хоста (`DetectConptyHost`: `WT_SESSION` → `TERM_PROGRAM` → класс окна `PseudoConsoleWindow`) → `g_console.mode`. `Fixed` — всё как сейчас (`system("mode con ...")`, шрифт 24px). `Adaptive` — размер и шрифт НЕ трогаем: в WT и размер буфера, и шрифт контролирует терминал (conpty). Диагностика показала: принудительная смена шрифта на 24px в conpty сбрасывала буфер к дефолтным 80×25 — отсюда «нет центрирования» и «нет предупреждения о размере». Фактический размер читается в `csbi` через `GetConsoleScreenBufferInfo`.
- [x] 3. **`DoubleBufferingBegin()`/`DoubleBufferingEnd()`:** `Fixed` — без изменений (включая `mode con` и копии между буферами). `Adaptive` — **двойная буферизация отключена**: `Begin` вызывает `UpdateAdaptiveBuffer()` (перечитывает размер, пересчитывает смещение, при ресайзе очищает буфер `FillConsoleOutputCharacterW`), `End` — no-op. Причина: кадр пишется в `basicBuffer` (через `wcout`/`SetConsoleCursorPosition`), а показывался `doubleBuffer` — отсюда артефакты и мерцание. Теперь рисуем напрямую в видимый буфер.
- [x] 4. **`ComputeCopyRegion`/`ComputeFrameOffset` в `Console.cpp`:** кадр 80×25 центрируется в буфере (`frameOffset = (bufW−80)/2, (bufH−25)/2`, если буфер меньше — 0 и кадр обрезается справа/снизу). В `Adaptive` используется только `frameOffset` (для `SetConsoleCursorPosition` в `ViewGameField`); область копирования `ReadConsoleOutput`/`WriteConsoleOutput` применяется только в `Fixed`.
- [x] 5. **`ViewGameField` (`GameField.cpp`):** `Fixed` — текущий код, символ в символ. `Adaptive` — `SetConsoleCursorPosition` на `(frameOffset.X, frameOffset.Y+row)` перед каждой строкой + обрезка строки по ширине буфера (`maxCols = bufW − ox`) + пропуск строк, выходящих за низ буфера (`bufRow >= bufHeight`), иначе `wcout` перенесёт хвост на следующую строку и кадр «поедет». Кадр по-прежнему 80×25, игровая логика и раскладка не меняются.
- [x] 6. **Проверка параметров окна на старте (только Adaptive):** `CheckWindowParameters` в `Splash.cpp` — **`MessageBoxW`** (гарантия видимости: строка в консоли в маленьком окне обрезается вьюпортом). Если `csbi.dwSize < 80×25` — «Увеличьте окно консоли хотя бы до 80x25 — поле будет обрезано». Проверку шрифта убрали: в conpty шрифт контролирует терминал, принудительно задать его нельзя, а поле корректно рисуется с любым шрифтом (просто плотнее/реже). В Fixed подсказки не показываются — поведение Win10/conhost не меняется.
- [x] 7. **Остаток меню паузы (только Adaptive):** кадр центрируется и не покрывает весь буфер, поэтому текст меню паузы (левый верхний угол, рисуется `ReturnToMenu` через `wcout`) оставался видимым после возврата в игру. Добавлена `ClearConsoleBuffer()` (`Console.h`/`Console.cpp`, no-op в Fixed) — вызывается в `Tetris.cpp` при `MenuResult::Stay`, до `CreateGameField`.

### Что не трогаем

- Игровая логика, `GAME_FIELD`, заставка (идёт через `ViewGameField` — подхватит режим сама).
- Меню: маленький текст в левом верхнем углу — корректен в обоих режимах, `system("cls")` работает и в WT.
- `mode con` в фиксированном пути — остаётся.
- Запрет ресайза окна — не делаем (в WT невозможно, в conhost не нужно).
- Truecolor — отдельная тема (ниже).

### Риски / открытые вопросы

- WT с окном уже 80 колонок — обрезка кадра (не масштабируем).
- Шрифт в WT задаёт пользователь: «поле под 24px» в WT не гарантируется — ограничение хоста, принимаем (проверку шрифта убрали, см. изменение №6).
- Установлено тестом: в WT буфер следует за окном (не сжимается ниже окна, но и не форсируется в 80×25, если мы не просим). Форсирование 80×25 при окне 50×15 давало скролл и подсказка не срабатывала — поэтому в Adaptive размер не форсируем.
- Установлено тестом: принудительная смена шрифта в conpty сбрасывает буфер к 80×25 — в Adaptive шрифт не трогаем (см. изменение №2).

## Заставка в маленьком окне (Adaptive) — отложено

При окне < 80×25 заставка урезана: логотип и ряд фигур не помещаются, заставка выглядит обрезанной. Подсказка `MessageBoxW` показывается, само игровое поле рисуется корректно (кадр обрезается справа/снизу). Не критично — отложено. Варианты: упрощённая заставка для узкого окна (только логотип в уменьшенном масштабе) или пропуск заставки при маленьком окне.

## Диагностические флаги — оставлено про запас

`--adaptive`/`--fixed`/`--diag` в `ProgramSettings()` (`Console.cpp`): ручное переопределение режима и диагностика в `tetris_diag.log` (рядом с exe) — `WT_SESSION`, `TERM_PROGRAM`, класс окна консоли, процесс-владелец окна, итоговый режим. Добавлены для проверки Adaptive-пути. Решение: оставить про запас (полезно для отладки и ручного переключения режима), убрать на более поздних этапах.

## Масштабирование кадра — отложено

Целочисленное масштабирование по ячейкам (2×, 3×: каждый логический пиксель — блок N×N из `█`; прецедент — логотип заставки с `scale = 2`) возможно и дёшево, но откладываем: либо лишнее, либо рано. Дробное масштабирование в текстовой консоли невозможно; масштаб шрифта — только в conhost (мы и так сами ставим 24px). Если делать — отдельным шагом: меняет и текст (счёт, подсказки), и рассинхронизирует меню (пишется мимо `ViewGameField`).

## Truecolor в консоли (заставка) — отложено

Заставка сейчас рисуется через `SetConsoleTextAttribute` (16 цветов, `enum Colors`). Truecolor (24-бит, ANSI/VT `\x1b[38;2;R;G;Bm`) доступен в Windows 10+ через `ENABLE_VIRTUAL_TERMINAL_PROCESSING`, но в нашем коде придётся учесть:

1. **Модель данных.** Цвета хранятся как 16-цветные индексы (`std::vector<int>`). Для настоящего truecolor нужно нести RGB. Либо маппить 16 индексов в конкретные RGB — тогда цвета те же, но пойдут через 24-битный путь (можно взять «правильные» RGB классической палитры тетромино, а не дефолтную раскраску консоли).
2. **Двойная буферизация.** Копия экрана между буферами идёт через `CHAR_INFO` (`ReadConsoleOutput`/`WriteConsoleOutput`), а он хранит только 16-цветные атрибуты. 24-бит в этой копии не удержится — этот путь для цветных пикселей придётся обойти или переделать.
3. **Unicode-режим** (`_O_U16TEXT`, вывод через `std::wcout`). VT-последовательности, записанные как wide-строки, консоль должна интерпретировать (обработка VT — на уровне подсистемы консоли, а не CRT). Это единственное, что стоит проверить коротким тестом, прежде чем на это опираться.
