## 1. В работе

### MCP: агент играет в Тетрис

Цель — LLM-агент (через MCP-клиент) играет в Тетрис сам; его ходы видны на игровом поле (идут через тот же движок, что и клавиатура). Сейчас агент — единственный игрок (ввод с клавиатуры в режиме `--agent` игнорируется); в будущем, когда добавим второго игрока, агент сможет играть за второго. MCP-клиент: плагин Visual Studio «LM Local» (первоочередной), сервер — по спецификации MCP (stdio), универсальный для любого MCP-клиента.

**Архитектура (3 слоя):**

1. **`TetrisEngine`** (`Core/TetrisEngine.h/.cpp`) — чистая игровая логика без I/O: состояние партии (стек, текущая/следующая фигура, счёт, уровень, game over/победа) + `Reset()`, `Step()`, `ApplyAction(Actions)`, `GetState()`. `PlayGame()` (`Tetris.cpp`) становится тонкой консольной обёрткой: цикл с `Sleep`, ввод, рендер поверх движка.
2. **Агентский канал в игре** — фоновый поток, TCP на `127.0.0.1:7777` (WinAPI-сокеты; `ws2_32.lib` — системная библиотека Windows, не внешняя зависимость). Протокол: строка = JSON. Флаг `--agent`: пропускает заставку и меню, сразу в игру; состояние движка под мьютексом.
3. **MCP-сервер** — режим того же `Tetris.exe` (`--mcp-server`): stdio JSON-RPC (MCP: `initialize`, `tools/list`, `tools/call`), сам подключается к агентскому каналу игры. Отдельный процесс обязателен: игра владеет консолью (`wcout`, `cls`, двойная буферизация) — stdio в том же процессе сломал бы рендер.

**Ключевые решения:**

- Транспорт — TCP на localhost: самый простой для отладки (netcat/PowerShell). Альтнатива — именованные каналы Windows (kernel32, без `ws2_32`), если сокеты окажутся проблемой.
- Порт занят: игра пробует 7777, затем 7778…7786 (первый свободный); все заняты — ошибка и выход. MCP-сервер сканирует тот же диапазон в том же порядке и подключается к первому ответившему.
- Ходы агента проходят через `TetrisEngine::ApplyAction` — тот же путь, что и клавиатура: видны на поле, подчиняются тем же правилам (столкновения, порядок действий).
- MCP-сервер — режим того же `Tetris.exe` (один исполняемый файл сохраняется), не новый проект в решении.
- Протокол: `{"id":1,"type":"get_state"}` — снапшот (board 10×22, текущая/следующая фигура: id + клетки `[x, y]`; счёт, уровень, game over); `{"id":2,"type":"get_rules"}` — правила игры и формат состояния (для LLM-агента); `{"id":3,"type":"action","action":"left|right|rotate_up|rotate_down|move_down|hard_drop"}`; `{"id":4,"type":"restart"}`; `{"id":5,"type":"quit"}` (завершить игру). Ответ — с тем же `id`.
- В режиме `--agent` после game over игра не блокируется на Enter — ждёт команду `restart` от агента.
- Тулзы MCP: `get_state`, `get_rules`, `move_left`, `move_right`, `rotate_up`, `rotate_down`, `move_down`, `hard_drop`, `restart`, `quit`.

**Темп агента (без гравитации):** в агентской игре нет ни таймера, ни гравитации — фигура висит, пока её не двигает агент (move_left/move_right, rotate_up/rotate_down, move_down — один ряд вниз, hard_drop — до упора). Темп партии = темп ходов агента (событийный цикл: ходы из очереди → применить → отрисовать → опубликовать состояние). Заменяет эксперимент «40 с на фигуру» (`AGENT_FIGURE_TIME_MS` — убирается подзадачей 7). Режим человека не меняется: гравитация и таймер `LEVEL_TIME_STEP` остаются.

**Продолжение (баги после первой игровой сессии агента):**
- Агент «не видел» game over: `session.SetState` не публиковался в ветке game over/победы — `get_state` возвращал `game_over: false`, и агент ходил ещё ~3 мин после экрана.
- Рестарт оставлял «хвост» экрана GAME OVER (правую часть, мерцал): игровой кадр `GAME_FIELD` шириной 45 колонок не перекрывает экран конца партии шириной 79 колонок (колонки 45..78).

#### Подзадача 8. Пакет шагов: расстановка фигуры одной командой (`place`)

Проблема (из первой игровой сессии агента): поодиночные ходы = 6–10 раундтрипов на фигуру (`get_state` + ходы + `hard_drop`). LLM-агент не держит темп (думает медленно, каждый ход — 1–2 с раундтрипа), а серии одинаковых вызовов (`move_down` × N, повторный `hard_drop`) упираются в защиту MCP-клиента от повторных одинаковых вызовов. Модель «сделал ход → жду ok → следующий ход» — узкое место: агент думает быстро, медлят раундтрипы.

Идея (пользователь): агент не делает поодиночные ходы, а одной командой присылает полную расстановку фигуры («котлету») — список ходов. Игра выполняет их по порядку, фиксирует фигуру и сразу возвращает новое состояние. Модель: «подумал один раз (в своём темпе — без гравитации/таймера) → исполнил пакетом → сразу увидел результат». Пакет = одна полная расстановка фигуры = одна фиксация — естественная единица действия агента.

Проект:

- [ ] Новая команда протокола: `{"id":N,"type":"place","actions":["left","left","rotate_down","down",...]}` — список ходов (тот же словарь: left/right/rotate_up/rotate_down/move_down/hard_drop).
- [ ] Выполнение: ходы по порядку, правила как у одиночных (`ApplyAction`, столкновения игнорируются); после пакета — фиксация фигуры, очистка линий, счёт/уровень, следующая фигура (или game over) — всё в том же вызове.
- [ ] Ответ: полное новое состояние (board, current, next, score, level, стёртые линии, прирост очков, game over, win) — агент сразу видит результат и планирует следующую фигуру.
- [ ] Политика фиксации (открытый вопрос — «а не глупо ли фиксировать»): (a) фиксировать на текущей позиции, даже если фигура висит в воздухе → «висячие» блоки, ломает семантику Тетриса (плохо); (b) только если уже села на дно; (c) после ходов игра сама опускает фигуру вертикально до упора (`hard_drop`) и фиксирует — без висячих, детерминированно, агенту не нужно считать ряды. Предпочтение — (c): пакет = позиционирование + ориентация, а опустить и зафиксировать — игра.
- [ ] MCP: тулз `place` (принимает список ходов) + описание в `tools/list`; `get_rules` — описать пакетную модель («подумал → расставил фигуру → увидел результат»).
- [ ] Поодиночные ходы остаются (отладка / ручная доводка); `place` — быстрый путь.
- [ ] Файлы: `AgentChannel.cpp` (команда, протокол, get_rules), `AgentGameSession` (пакет в очереди — новый тип «batch»), `AgentGame.cpp` (выполнение пакета циклом), `McpServer.cpp` (тулз `place`), README, `DevDocs/mcp-agent.md`.
- [ ] Сборка без ошибок и предупреждений.
- [ ] Ручная проверка: агент играет через `place` (одна команда на фигуру), повторных одинаковых вызовов нет, темп приемлемый.

## 2. Отложенные

### Масштабирование кадра

Целочисленное масштабирование по ячейкам (2×, 3×: каждый логический пиксель — блок N×N из `█`; прецедент — логотип заставки с `scale = 2`) возможно и дёшево, но откладываем: либо лишнее, либо рано. Дробное масштабирование в текстовой консоли невозможно; масштаб шрифта — только в conhost (мы и так сами ставим 24px). Если делать — отдельным шагом: меняет и текст (счёт, подсказки), и рассинхронизирует меню (пишется мимо `ViewGameField`).

### Truecolor в Fixed (conhost)

Truecolor (24-бит, VT `\x1b[38;2;R;G;Bm`) введён только для Adaptive (Windows Terminal): в `ProgramSettings()` VT включается и флаг `g_console.truecolor` ставится только для Adaptive. В Fixed (conhost) truecolor не работает — 16-цветный путь через `SetConsoleTextAttribute` остаётся как есть. Причина: конвейер Fixed идёт через двойную буферизацию (`CHAR_INFO` хранит только 16-цветные атрибуты, 24-бит в копии между буферами не удержится) — этот путь для truecolor придётся переделывать. Отложено: сначала отработаем truecolor в WT.

- Заставка в маленьком окне (Adaptive) — при окне < 80×25 заставка пропускается (была бы обрезана); `MessageBoxW` остаётся — документация — `DevDocs/adaptive-rendering.md` (решение 6).
- Адаптивный рендер для Windows Terminal — закоммичено (2026-10-26, `3b564ec`), документация — `DevDocs/adaptive-rendering.md`.
- Двойная буферизация в Adaptive — кадр появляется атомарно (без «рулона»/мерцания), truecolor-кадр через `WriteConsoleW`/`prevFrame`, ресайз без мерцания; проверено в WT — документация — `DevDocs/adaptive-rendering.md` (решения 2, 5).
- Стартовое мерцание в Fixed (conhost) — ранний `mode con` до создания `doubleBuffer` (только Fixed) + выравнивание окон буферов; проверено в conhost — документация — `DevDocs/adaptive-rendering.md` (решение 3).
- Truecolor в консоли (Windows Terminal / Adaptive) — truecolor (24-бит) в WT: заставка, игровые кадры, экраны Game Over / You Win, вспышка level up, условие победы (25-й уровень / счёт 8000); документация — `DevDocs/truecolor-console.md`.
- Половинные блоки в заставке — логотип и ряд фигур на `▀ ▄ █` (квадратные пиксели, двойное вертикальное разрешение); документация — `DevDocs/half-blocks-splash.md`.
- Заставки: финальные экраны (половинные блоки) + меню глифами (на русском) — «GAME OVER» / «YOU WIN» на `▀ ▄ █`, меню (заголовок и пункты) на кириллических глифах 5×7; документация — `DevDocs/pixel-menu.md`, `DevDocs/half-blocks-splash.md`.
