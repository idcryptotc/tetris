## 1. В работе

### MCP: агент играет в Тетрис

Цель — LLM-агент (через MCP-клиент) играет в Тетрис сам; его ходы видны на игровом поле (идут через тот же движок, что и клавиатура). Сейчас агент — единственный игрок (ввод с клавиатуры в режиме `--agent` игнорируется); в будущем, когда добавим второго игрока, агент сможет играть за второго. MCP-клиент: плагин Visual Studio «LM Local» (первоочередной), сервер — по спецификации MCP (stdio), универсальный для любого MCP-клиента.

**Архитектура (3 слоя):**

1. **`TetrisEngine`** (`Core/TetrisEngine.h/.cpp`) — чистая игровая логика без I/O: состояние партии (стек, текущая/следующая фигура, счёт, уровень, game over/победа) + `Reset()`, `Step()`, `ApplyAction(Actions)`, `GetState()`. `PlayGame()` (`Tetris.cpp`) становится тонкой консольной обёрткой: цикл с `Sleep`, ввод, рендер поверх движка.
2. **Агентский канал в игре** — фоновый поток, TCP на `127.0.0.1:7777` (WinAPI-сокеты; `ws2_32.lib` — системная библиотека Windows, не внешняя зависимость). Протокол: строка = JSON. Флаг `--agent`: пропускает заставку и меню, сразу в игру; состояние движка под мьютексом.
3. **MCP-сервер** — режим того же `Tetris.exe` (`--mcp-server`): stdio JSON-RPC (MCP: `initialize`, `tools/list`, `tools/call`), сам подключается к агентскому каналу игры. Отдельный процесс обязателен: игра владеет консолью (`wcout`, `cls`, двойная буферизация) — stdio в том же процессе сломал бы рендер.

**Ключевые решения:**

- Транспорт — TCP на localhost: самый простой для отладки (netcat/PowerShell). Альтнатива — именованные каналы Windows (kernel32, без `ws2_32`), если сокеты окажутся проблемой.
- Порт занят: игра пробует 7777, затем 7778…7786 (первый свободный); все заняты — ошибка и выход. MCP-сервер сканирует тот же диапазон в том же порядке и подключается к первому ответившему.
- Ходы агента проходят через `TetrisEngine::ApplyAction` — тот же путь, что и клавиатура: видны на поле, подчиняются тем же правилам (столкновения, порядок действий).
- MCP-сервер — режим того же `Tetris.exe` (один исполняемый файл сохраняется), не новый проект в решении.
- Протокол: `{"id":1,"type":"get_state"}` — снапшот (board 10×22, текущая/следующая фигура: id + клетки `[x, y]`; счёт, уровень, game over); `{"id":2,"type":"get_rules"}` — правила игры и формат состояния (для LLM-агента); `{"id":3,"type":"action","action":"left|right|rotate_up|rotate_down|hard_drop"}`; `{"id":4,"type":"restart"}`; `{"id":5,"type":"quit"}` (завершить игру). Ответ — с тем же `id`.
- В режиме `--agent` после game over игра не блокируется на Enter — ждёт команду `restart` от агента.
- Тулзы MCP: `get_state`, `get_rules`, `move_left`, `move_right`, `rotate_up`, `rotate_down`, `hard_drop`, `restart`, `quit`.

**Темп:** фиксированный — 40 с на фигуру (`AGENT_FIGURE_TIME_MS` в `AgentGame.cpp`), не зависит от уровня: темп человека (`LEVEL_TIME_STEP`) агенту не подходит, MCP-раундтрип занимает секунды. «Шаговый режим» (пауза + один шаг на команду) — отдельная идея, если понадобится.

## 2. Отложенные

### Масштабирование кадра

Целочисленное масштабирование по ячейкам (2×, 3×: каждый логический пиксель — блок N×N из `█`; прецедент — логотип заставки с `scale = 2`) возможно и дёшево, но откладываем: либо лишнее, либо рано. Дробное масштабирование в текстовой консоли невозможно; масштаб шрифта — только в conhost (мы и так сами ставим 24px). Если делать — отдельным шагом: меняет и текст (счёт, подсказки), и рассинхронизирует меню (пишется мимо `ViewGameField`).

### Truecolor в Fixed (conhost)

Truecolor (24-бит, VT `\x1b[38;2;R;G;Bm`) введён только для Adaptive (Windows Terminal): в `ProgramSettings()` VT включается и флаг `g_console.truecolor` ставится только для Adaptive. В Fixed (conhost) truecolor не работает — 16-цветный путь через `SetConsoleTextAttribute` остаётся как есть. Причина: конвейер Fixed идёт через двойную буферизацию (`CHAR_INFO` хранит только 16-цветные атрибуты, 24-бит в копии между буферами не удержится) — этот путь для truecolor придётся переделывать. Отложено: сначала отработаем truecolor в WT.

## 3. Оставлено про запас (диагностика)

### Диагностические флаги

`--adaptive`/`--fixed`/`--diag` в `ProgramSettings()` (`Console.cpp`): ручное переопределение режима и диагностика в `tetris_diag.log` (рядом с exe) — `WT_SESSION`, `TERM_PROGRAM`, класс окна консоли, процесс-владелец окна, итоговый режим. Добавлены для проверки Adaptive-пути. Решение: оставить про запас (полезно для отладки и ручного переключения режима), убрать на более поздних этапах.
