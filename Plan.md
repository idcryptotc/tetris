# Plan.md — отложенные мысли и планы

Место для «отложенных» мыслей и идей, которые пока не реализованы, и для текущего плана работы. Агенты: перед началом работы по отложенной идее сверяйтесь с этим файлом. Статусы: «в работе» — план согласован, реализуется; «отложено» — идея зафиксирована, пока не берёмся.

## Адаптивный рендер для Windows Terminal — В РАБОТЕ

**Проблема.** Строка `system("mode con cols=80 lines=25")` в Windows 11 в Windows Terminal не работает (в консоли Win10 — работает). Терминал содержит вкладки, его размер меняется пользователем; запретить ресайз окна и убрать вкладки из кода приложения нельзя (окно принадлежит хосту). Принудительно сменить хост (например, в conhost) из кода тоже нельзя — это настройка ОС («Терминал по умолчанию»).

**Решение.** Текущий режим (фиксированные 80×25 через `mode con`) остаётся без изменений — в Win10/conhost он работает. Параллельно добавляется второй, адаптивный, режим. Выбор — рантайм-детект Windows Terminal (не по версии ОС: WT есть на Win10, conhost — на Win11). Механизм переопределения (флаг ОС / условная компиляция) решим позже — код строится так, чтобы решение стоило 5 строк.

### Детект хоста

- `GetEnvironmentVariableW(L"WT_SESSION")` — переменную задаёт WT всем хостируемым процессам (задокументировано в WT);
- запасной — `TERM_PROGRAM == WindowsTerminal`.

### Изменения

1. **`Console.h`:** `enum class ConsoleMode { Fixed, Adaptive }` (Fixed = текущий); в `ConsoleRenderer` — поле `mode` и фактический размер буфера (заодно исправить мёртвое `csbi` — оно никогда не инициализировалось, а `DoubleBufferingBegin` передаёт `{0,0}` в `SetConsoleScreenBufferSize`).
2. **`ProgramSettings()`:** детект WT → `g_console.mode`. `Fixed` — всё как сейчас (`system("mode con ...")`). `Adaptive` — размер через `SetConsoleScreenBufferSize` + `SetConsoleWindowInfo` (в conhost сработает, в WT тихо не сработает — ок). В обоих режимах читать фактический размер в `csbi` через `GetConsoleScreenBufferInfo`.
3. **`DoubleBufferingBegin()`:** `Fixed` — без изменений (включая `mode con`); `Adaptive` — восстановление размера через WinAPI с реальным `csbi.dwSize`, без `system`.
4. **`ViewGameField` (`GameField.cpp`):** `Fixed` — текущий код, символ в символ. `Adaptive` — центрирование кадра 80×25 в реальном буфере: `ox = (bufW − 80) / 2`, `oy = (bufH − 25) / 2` (если окно меньше — 0, кадр обрезается справа/снизу), `SetConsoleCursorPosition` на начало каждой строки. Кадр по-прежнему 80×25, игровая логика и раскладка не меняются.
5. **Проверка параметров окна на старте (только Adaptive):** буфер ≥ 80×25 (`GetConsoleScreenBufferInfo`) и высота шрифта = 24px (`GetCurrentConsoleFontEx`, фактические пиксели — зависят от шрифта и DPI). При провале — подсказка строкой внизу заставки (она висит до нажатия клавиши, подходящий момент): «увеличьте окно хотя бы до 80×25» / «задайте шрифт высотой 24px в настройках Terminal». В Fixed подсказки не показываются — поведение Win10/conhost не меняется.

### Что не трогаем

- Игровая логика, `GAME_FIELD`, заставка (идёт через `ViewGameField` — подхватит режим сама).
- Меню: маленький текст в левом верхнем углу — корректен в обоих режимах, `system("cls")` работает и в WT.
- `mode con` в фиксированном пути — остаётся.
- Запрет ресайза окна — не делаем (в WT невозможно, в conhost не нужно).
- Truecolor — отдельная тема (ниже).

### Риски / открытые вопросы

- WT с окном уже 80 колонок — обрезка кадра (не масштабируем).
- Двойная буферизация через `ReadConsoleOutput`/`WriteConsoleOutput` в conpty — теоретически должна работать, обязательно проверить запуском в WT.
- Шрифт в WT задаёт пользователь: «поле под 24px» в WT не гарантируется — ограничение хоста, принимаем.

### Финализация

- Сборка Win32/x64, Debug/Release — без ошибок и предупреждений.
- Тесты: Win10 + conhost (Fixed-путь не изменился), WT (Adaptive-путь).
- `README.md` и инварианты в `AGENTS.md` (сейчас жёстко «`mode con cols=80 lines=25`») — обновить под два режима.

## Масштабирование кадра — отложено

Целочисленное масштабирование по ячейкам (2×, 3×: каждый логический пиксель — блок N×N из `█`; прецедент — логотип заставки с `scale = 2`) возможно и дёшево, но откладываем: либо лишнее, либо рано. Дробное масштабирование в текстовой консоли невозможно; масштаб шрифта — только в conhost (мы и так сами ставим 24px). Если делать — отдельным шагом: меняет и текст (счёт, подсказки), и рассинхронизирует меню (пишется мимо `ViewGameField`).

## Truecolor в консоли (заставка) — отложено

Заставка сейчас рисуется через `SetConsoleTextAttribute` (16 цветов, `enum Colors`). Truecolor (24-бит, ANSI/VT `\x1b[38;2;R;G;Bm`) доступен в Windows 10+ через `ENABLE_VIRTUAL_TERMINAL_PROCESSING`, но в нашем коде придётся учесть:

1. **Модель данных.** Цвета хранятся как 16-цветные индексы (`std::vector<int>`). Для настоящего truecolor нужно нести RGB. Либо маппить 16 индексов в конкретные RGB — тогда цвета те же, но пойдут через 24-битный путь (можно взять «правильные» RGB классической палитры тетромино, а не дефолтную раскраску консоли).
2. **Двойная буферизация.** Копия экрана между буферами идёт через `CHAR_INFO` (`ReadConsoleOutput`/`WriteConsoleOutput`), а он хранит только 16-цветные атрибуты. 24-бит в этой копии не удержится — этот путь для цветных пикселей придётся обойти или переделать.
3. **Unicode-режим** (`_O_U16TEXT`, вывод через `std::wcout`). VT-последовательности, записанные как wide-строки, консоль должна интерпретировать (обработка VT — на уровне подсистемы консоли, а не CRT). Это единственное, что стоит проверить коротким тестом, прежде чем на это опираться.
